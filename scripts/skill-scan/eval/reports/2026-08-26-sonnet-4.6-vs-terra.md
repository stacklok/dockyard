# Skill scanner model evaluation: Sonnet 4.6 vs GPT-5.6 Terra

Date: 2026-08-26

Tracking issue: [#909](https://github.com/stacklok/dockyard/issues/909)

## Decision

Use `openai/gpt-5.6-terra` for the skill-security-scan LLM analyzer as a
single-run configuration, then monitor the first several production PRs.
Do not enable consensus runs initially: Terra matched Sonnet 4.6 on every
fixture-level malicious/safe decision, while consensus would give back much
of the latency and cost advantage.

## Configuration

- Scanner: `cisco-ai-defense/skill-scanner` 2.0.13
- Production wrapper: `scripts/skill-scan/run_scan.py`
- Models: `anthropic/claude-sonnet-4-6`, `openai/gpt-5.6-terra`
- Repetitions: three per fixture or Dockyard skill
- Dockyard corpus: nine skills at the refs pinned in `spec.yaml` on the
  evaluation date
- Recall corpus: the 12 safe and malicious fixtures bundled with scanner
  2.0.13

The scanner's bundled `evals/runners/benchmark_runner.py` was not used for
the recall comparison because it does not enable the LLM or meta analyzers.
The fixtures were instead scanned through Dockyard's production wrapper.

## Recall results

| Metric | Sonnet 4.6 | GPT-5.6 Terra |
|---|---:|---:|
| Malicious fixtures blocked | 30/30 | 30/30 |
| Safe fixtures clean at HIGH+ | 6/6 | 6/6 |
| Expected finding slots covered at any severity | 63/78 | 61/78 |
| Expected finding slots covered at HIGH+ | 60/78 | 48/78 |
| Total wall time, 36 scans | 2,437s | 1,216s |
| Input tokens | 495,129 | 404,396 |
| Output tokens | 123,949 | 83,969 |

Terra preserved every fixture-level decision. Sonnet retained more expected
categories at blocking severity, so Terra's lower HIGH+ category coverage is
the principal recall caveat. It did not translate into a missed malicious
fixture or a false positive on a safe fixture.

## Dockyard stress results

The corpus was `claude-api`, `find-bugs`, `pulumi-upgrade-provider`,
`provider-upgrade`, `huggingface-paper-publisher`, `codeql`, `semgrep`,
`supply-chain-risk-auditor`, and `zeroize-audit`.

| Metric | Sonnet 4.6 | GPT-5.6 Terra |
|---|---:|---:|
| Successful scans | 27/27 | 27/27 |
| Total wall time | 8,089s | 4,451s |
| Mean LLM finding-set Jaccard | 0.511 | 0.419 |
| Input tokens | 2,960,689 | 2,487,843 |
| Output tokens | 489,470 | 385,736 |

Terra was about 1.8 times faster on the Dockyard corpus and about twice as
fast on the recall corpus. Sonnet had better nominal finding-set stability.

### Stability by skill

| Skill | Sonnet 4.6 | GPT-5.6 Terra |
|---|---:|---:|
| `claude-api` | 0.292 | 0.111 |
| `find-bugs` | 0.667 | 1.000 |
| `pulumi-upgrade-provider` | 0.867 | 0.194 |
| `provider-upgrade` | 0.413 | 0.289 |
| `huggingface-paper-publisher` | 0.565 | 0.667 |
| `codeql` | 0.333 | 0.333 |
| `semgrep` | 0.482 | 0.181 |
| `supply-chain-risk-auditor` | 0.522 | 1.000 |
| `zeroize-audit` | 0.460 | 0.000 |

The stability gap was not confined to one pathological skill. Sonnet was
more stable on five skills, Terra was more stable on three, and CodeQL tied.
Sonnet's aggregate advantage therefore represents a real tradeoff rather
than a single-skill outlier. Stability was not treated as the only decision
criterion because Jaccard measures rule-ID and file-anchor agreement, not
whether a changing finding is semantically useful or a false positive.

Finding-level review changed the interpretation of aggregate block counts:

- Terra consistently elevated the untrusted Cargo build and compiler-plugin
  execution boundaries in `zeroize-audit`. Sonnet described related paths
  but kept them below the blocking threshold.
- Terra identified plausible unquoted-parameter and mutable-ruleset risks in
  `semgrep`. These require trust decisions and should not be counted as
  automatic false positives.
- Sonnet produced new `LLM_DATA_EXFILTRATION` blockers on unchanged
  `huggingface-paper-publisher` content in two of three runs. They treated
  normal `HF_TOKEN` authentication plus Hugging Face API access as possible
  exfiltration.
- The Sonnet CodeQL pipeline produced 0, 17, and 17 raw HIGH+ findings across
  three unchanged runs. Much of the burst came from nondeterministic static
  rules, so it cannot all be attributed to the model; it still demonstrates
  that retaining Sonnet does not remove pipeline churn.

## Cost estimate

At the providers' base list prices on the evaluation date, the newly run
recall and fresh Sonnet scans cost approximately $21.40. Including the prior
Terra Dockyard scans used in the comparison, the complete compared dataset
represents approximately $31. Provider billing is authoritative because
caching and per-request long-context tiers are not fully represented by the
aggregate usage fields.

## Limitations

- The recall corpus is small and synthetic. This is a practical migration
  gate, not a statistical equivalence proof.
- The scanner pipeline itself is nondeterministic, including non-LLM rules.
  Sequential model runs cannot attribute every cross-run difference to the
  selected model.
- The Dockyard corpus contains trusted skills rather than known malware.
  Aggregate blockers therefore require finding-level review: a higher count
  can be a useful detection, while a lower count can be a miss.
- Raw scan JSON is intentionally not committed. It is large, contains cloned
  third-party source paths, and is reproducible with `bench_models.py` and
  `bench_recall.py`. This report preserves the durable comparison record.
